Designing quarterly progress reports that actually align to licensure standards

Duccio Mondanelli · 2026 · ~8 min read

!

Watch your steps! This is a construction zone. This case study is actually a work in progress right now.

Every apprenticeship (but really, every program worth its salt) needs a quarterly report. In my experience, though, few of them can answer the only question they exist to ask: Is this person on track for this specific license?

Ours could not either, at first. This is how we rebuilt it.

The classic problem: one generic form for two different licenses

We run two Minnesota tracks. ABS is K-12. ECSE is birth to six. Those are different jobs. IFSPs and family coaching versus FBAs, BIPs, and K-12 IEPs. Toddlers vs teenagers. New parents vs experienced caregivers.

Our old form treated them the same. Four vague buckets like "foundational knowledge." They mapped to no actual standard. It never distinguished an IFSP from an IEP. As a former mentor with no time left for BS forms, I would have filled it out because I had to. And the resulting data would have told us almost nothing.

A report mentors cannot complete accurately will not measure anything. It just creates the feeling of data.

The redesign

We made four decisions to improve these documents.

1. Split the form

First, split the form. One instrument per license, visually distinct at a glance. One size fits all confused everyone, starting with mentors. The visual piece was essential. No more "which form is which again?" when you are sending a last minute update. Colors are used to create clarity, implementing core ideas of intentional design in a space often constrained by academic and institutional bindings.

The obvious idea

Each program needs its own visual identity and set of tools. One size fits all ends up confusing everyone, starting with the mentors.

2. Map every item to a real standard

Second, map every item to a real standard or cut it. Every content item on each form now traces to something a licensing body or the program itself actually requires: Minnesota's PELSB standards for each license, the program's core skills, and High Leverage Practices. If an item couldn't be traced, it got cut.

One rule from that process worth borrowing: use only the frameworks your program has actually adopted. Our first draft kept a respected national framework that we realize our program does not actually use. What it did was create confusion and waste time for everyone.

The obvious idea

Everything tracked must be actual worthwhile data. Stop tracking stuff you don't need "just in case".

3. Build in progression

Third, build in progression. Same questions in quarter one and seven show us the journey. The answers are what drives the alarms. We wrote explicit expectations by phase, from observation through co-teaching to independent practice, so a "developing" rating in an early quarter reads as normal and the same rating in a late quarter reads as a flag.

The obvious idea

If we ask the same questions in different quarters, we're likely to get the same answers.

4. Design for thirty seconds

Fourth, design for thirty seconds. The reader is a mentor with a full caseload. Dropdowns over free text. Grouping that matches an observation flow. Nothing that needs them to lookup anything. We built the documents programmatically, which meant we could also do things standard templates can't, like styling dropdowns so they're impossible to miss.

The obvious idea

If the busiest person in the loop can't complete the instrument accurately in one sitting, it's the instrument that is wrong.

What I'd tell another program

If you serve multiple licenses, you need multiple tools. Link all items or cut them. Show the quarter in the form. Optimize for the busiest person in the loop.

If the mentor is overwhelmed, there is no data to analyze. If you are fixing instruments like this, I am happy to compare notes. Find me on LinkedIn.
